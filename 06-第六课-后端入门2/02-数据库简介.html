分类

数据库的两大类别

主流数据库 · 分类用途场景
对比
关系型非关系型 NoSQL
组织方式表、行、列，键关联文档、键值、宽列、图
擅长业务关联、事务、约束灵活结构、特定访问模式
代表MySQL、PostgreSQLMongoDB、Redis、Cassandra、Neo4j
举例订单、库存、财务商品属性、缓存、事件、关系网
通俗解释
  • 关系型像一组相互关联的登记表：用户表记"谁"，订单表记"买了什么"，商品表记"卖什么"。
  • 非关系型各有不同组织方式：文档像商品档案，键值像编号取物，图像人物关系网。
讲解要点

按数据模型分类，不等同于"慢与快"或"老与新"；NoSQL 并非不能支持事务，支持范围看具体产品；产品能力会重叠——关系型也能处理 JSON，部分产品也支持向量检索。

02
关系型数据库

记录核心业务，保证数据正确

主流数据库 · 分类用途场景
MySQL
常见的业务"账本"

存什么：用户资料、商品价格、订单明细、库存数量、支付状态。

做什么：注册新增用户、浏览查商品、下单写订单、取消订单恢复库存。

例子：买两件商品时，创建订单和扣减库存应协调完成，避免"订单创建了，库存却没扣"。

PostgreSQL
"账本" + 丰富的查询工具

存什么：相似业务数据，也支持 JSON；地理空间可用 PostGIS 扩展。

做什么：多表关联、复杂统计、结构化与 JSON 混合查询、地理查询。

例子：统计各城市销量、分析用户复购、查询距顾客 3 公里内的门店。

讲解要点

两者用途大量重叠：MySQL 也能做复杂查询，PostgreSQL 也能承担普通网站业务。最终选择还取决于团队经验、工具生态和维护成本；事务不自动覆盖外部支付平台，支付与订单仍需业务流程协调。

03
非关系型数据库

NoSQL：按数据特点分工

主流数据库 · 分类用途场景
MongoDB
文档型 · 结构各异的档案

存：类 JSON 文档（实际为 BSON），含嵌套属性与标签。

做：按字段查询更新、聚合统计，适应字段调整。

例：服装存尺码面料，手机存芯片电池，不必共用同一组字段。

Redis
键值型 · 热点数据快速取出

存：键值与字符串、哈希、列表、集合、有序集合。

做：缓存热门查询、登录会话、计数、热销排行榜。

例：热门商品介绍缓存进 Redis，减少主库重复查询。

Cassandra
宽列型 · 持续产生的海量记录

存：按分区组织的大规模记录，如设备与行为事件。

做：分散到多台机器，承接大规模写入，按预设分区键查询。

例：按"某设备、某时间段"读取持续上报的运行状态。

Neo4j
图数据库 · 谁和谁有关

存：节点、关系和属性，如用户节点与"使用过"关系。

做：查询多层关联、关系路径和共同关联对象。

例：多账号共享设备或手机号，沿关系网发现刷单团伙。

讲解要点

NoSQL 是多种数据库的集合，各自解决不同问题：灵活结构仍需数据设计与校验；缓存要考虑更新与失效；宽列建表围绕查询方式设计；图数据库的优势在关系分析，简单订单记录不必改用它。

协同

一个系统如何让多种数据库配合工作

主流数据库 · 分类用途场景
以电商平台为例：每类数据有明确职责和权威来源
系统任务可使用的数据库分工与价值
下单、管理库存、记录支付结果MySQL / PostgreSQL核心业务主库，保存订单、价格、可售库存，用事务协调更新
展示不同品类的商品参数MongoDB（按需）保存灵活的商品属性，通过商品 ID 与主库关联
快速展示热点商品、维护会话Redis缓存热门数据、会话和排行，失效时回源读取
搜索"红色运动鞋"Elasticsearch（按需）建立搜索索引，提供全文搜索、筛选与相关性排序
AI 问答、按含义查找商品Milvus 等向量库（按需）保存向量及关联 ID，查找语义相近内容，为 AI 提供检索材料
页内流程

浏览 → 查缓存/商品资料；搜索 → 查搜索索引；下单 → 写业务主库；数据更新 → 同步缓存和索引。数据库的选择由后端完成，用户只看到一个商城。

落地

数据如何流动，以及如何渐进式选型

主流数据库 · 分类用途场景
一次改价后的数据流动
先更新权威主库→ 再更新缓存和索引→ 失败则重试+定期核对

主库事务通常不覆盖缓存、搜索和向量库，副本可能短暂滞后；浏览和搜索可容忍延迟，下单必须重新校验权威记录。

同步手段

消息队列、变更事件或定时任务，避免每次请求同时写入所有数据库。

不是每个系统都需要全部数据库
  • 小型商城：一套 MySQL 或 PostgreSQL 就够了
  • 访问量上升：重复读取成瓶颈，再加 Redis 缓存
  • 搜索要求提升：需要全文检索时引入搜索引擎
  • 属性或 AI 需求出现：再评估文档存储和向量检索

每加一种数据库，都带来部署、监控、备份、权限和同步成本。

页尾结论

从主库开始，遇到明确需求再增加专用数据库，同时管理好数据同步。
