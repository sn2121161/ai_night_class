# shop 服务器容器化部署方案

> 状态：规划稿；本文不代表已经执行部署。  
> 调研时间：2026-10-09。  
> 应用源码：<https://github.com/sn2121161/shop>（调研基准 commit：`f6bf98d`）。

## 1. 目标与边界

将 `shop` 以一套独立的 Docker Compose 服务部署到现有 Ubuntu 服务器，并满足：

- 现有站点不停机、不抢占已有 Apache 的 `80/443` 端口；
- 商城 API、PostgreSQL、上传文件和密钥彼此隔离；
- Mac 开发环境与 Ubuntu 生产环境使用同一套代码、同一组数据库迁移，但使用各自独立的数据库；
- 每次发布都是一个可识别、可回滚的版本，不在生产服务器直接修改源码；
- 数据库结构变更通过 Alembic migration 串行执行，而非依赖应用启动时的临时建表逻辑。

本文推荐的生产拓扑如下：

```text
Internet
   |
   | HTTPS :443，商城独立域名，例如 shop.example.com
   v
现有宿主机 Apache（继续管理 TLS 与域名路由）
   |-- /        -> 127.0.0.1:3000（前端容器）
   `-- /api/    -> 127.0.0.1:5600（API 容器）
                         |
                         v
                Docker Compose：shop
                  |-- api：FastAPI + Uvicorn + Alembic
                  |-- db ：PostgreSQL 16（仅 Docker 内部网络）
                  `-- frontend：Vinext 前端应用

持久化资源（不在镜像中）：
  /srv/shop/.env.production       生产密钥与连接配置
  Docker volume: shop_postgres    PostgreSQL 数据
  Docker volume: shop_uploads     评论/商品上传文件
  /srv/shop/backups               数据库备份
```

前端作为普通 Node 应用容器运行；容器中**不配置公网 Nginx 或 Apache**。宿主机已有 Apache 继续唯一占用公网 `80/443`，反代到本机的前端和 API 端口。

## 2. 已核实的服务器情况

### 2.1 资源与系统

| 项目 | 实测结果 | 结论 |
|---|---|---|
| 系统 | Ubuntu 24.04 LTS，x86_64，腾讯云 CVM | 与 Docker、PostgreSQL 16 兼容 |
| CPU | 4 vCPU | 足以支撑小中等访问量的单实例商城 |
| 内存 | 3.6 GiB；巡检时约 2.5 GiB 可用 | 可运行 API + PostgreSQL；需设容器资源上限并观测 |
| 磁盘 | 40 GiB；约 28 GiB 可用 | 初期够用；上传文件和备份须监控增长 |
| Swap | 1.9 GiB | 可缓冲短暂内存峰值，但不能替代扩容 |

### 2.2 现有服务与端口

| 资源 | 当前状态 | 对部署的影响 |
|---|---|---|
| Apache（Lighthouse） | 已监听公网 `80/443` | 商城应新增 Apache 虚拟主机，不能在容器映射 `80/443` |
| Nginx | 已监听 `8000` | 与商城无关，不应改动 |
| MariaDB | 监听 `3306` | 商城不复用它；项目要求 PostgreSQL |
| Python | 3.12.3 | 可用于辅助脚本；正式 API 放入容器 |
| Node | 用户 nvm 下有 Node 24.19.0 | 仅用于既有环境，不能当作 systemd/生产构建的隐式依赖 |
| Docker | 未安装 | 首次实施时需要安装 Docker Engine 与 Compose 插件 |
| PostgreSQL | 未安装 | 由 `db` 容器提供，不安装宿主机 PostgreSQL |

现有 Apache 已托管其他域名，并已有到本机 `127.0.0.1:9300` 的反向代理，说明“Apache 为不同域名反代本机服务”的方式与当前环境兼容。

### 2.3 上线前必须处理的安全基线

以下是只读巡检发现的现状，实施前应先确认腾讯云安全组与变更窗口：

- UFW 当前未启用；
- MariaDB 在公网地址监听 `3306`；
- SSH 当前允许密码认证、root 登录和 X11 转发；
- 系统存在较多可升级包，包括内核、安全组件、OpenSSH 与 Nginx。

建议将“系统升级/可能重启”与商城首发分为两个维护窗口。商城部署窗口只需保证云安全组开放 `80/443`；SSH 的 `22` 应限制为固定办公出口 IP。PostgreSQL 容器不映射公网端口。MariaDB 的暴露收口需要确认是否影响已有应用后单独处理。

## 3. 当前仓库的部署前置修改

仓库当前没有 Dockerfile、Compose、systemd 或 Web 服务器配置，需要补齐以下内容。

### 3.1 必须修正的生产配置

1. 前端当前默认请求 `http://localhost:5600/api`。生产构建必须改为由环境变量控制，例如：

   ```bash
   NEXT_PUBLIC_API_URL=/api
   ```

   使用相对路径可避免把正式域名写死在前端构建产物中。

2. 后端 CORS 当前仅允许本地开发地址。应改为读取 `CORS_ORIGINS`，生产值为：

   ```bash
   CORS_ORIGINS=https://shop.example.com
   ```

3. 后端的数据库初始化逻辑不应作为生产结构升级机制。引入 Alembic，并把未来每一次建表、加列、索引、数据修复写入 migration 文件。

### 3.2 生产环境变量

提交 `.env.example`，只放变量名和无敏感示例值；以下两个文件必须加入 `.gitignore`：`.env.local`、`.env.production`。

```bash
# .env.example（可以提交）
DATABASE_URL=
JWT_SECRET=
PAYMENT_ENCRYPTION_KEY=
COMMENT_UPLOAD_DIR=/app/uploads
CORS_ORIGINS=
# 可选：飞书集成变量
FEISHU_APP_ID=
FEISHU_APP_SECRET=
FEISHU_...=
```

生产服务器的 `/srv/shop/.env.production` 示例：

```bash
DATABASE_URL=postgresql+psycopg2://shop_prod:<高强度密码>@db:5432/shop_prod
JWT_SECRET=<至少32字节的随机密钥>
PAYMENT_ENCRYPTION_KEY=<符合应用要求的随机加密密钥>
COMMENT_UPLOAD_DIR=/app/uploads
CORS_ORIGINS=https://shop.example.com
```

注意：在 API 容器中，`localhost` 指向 API 容器自身；连接 Compose 内 PostgreSQL 必须使用主机名 `db`。密码仅保留在服务器 `.env.production` 中，权限设为 `600`，绝不提交 GitHub。

## 4. 容器设计

### 4.1 服务职责

| 服务 | 运行内容 | 端口暴露 | 持久化 |
|---|---|---|---|
| `api` | FastAPI、Uvicorn、Alembic、应用代码 | 仅 `127.0.0.1:5600` | `shop_uploads` |
| `db` | PostgreSQL 16 | 不映射到宿主机 | `shop_postgres` |
| `frontend` | Vinext 前端应用 | 仅 `127.0.0.1:3000` | 无 |
| Apache（宿主机） | TLS、域名虚拟主机、反向代理 | 公网 `80/443` | 不适用 |

不要将 PostgreSQL 的 `5432` 映射为 `0.0.0.0:5432`，也不要让商城容器监听 `80/443`。

### 4.2 建议的 Compose 基线

以下是目标结构示例，实际 Dockerfile、健康检查路径和镜像仓库名称应与代码落地后一致：

```yaml
services:
  api:
    image: ghcr.io/<github-owner>/shop-api:${IMAGE_TAG}
    env_file: /srv/shop/.env.production
    command: uvicorn app:app --host 0.0.0.0 --port 5600
    ports:
      - "127.0.0.1:5600:5600"
    volumes:
      - shop_uploads:/app/uploads
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
    cpus: 1.0
    mem_limit: 768m

  db:
    image: postgres:16
    env_file: /srv/shop/.env.production
    volumes:
      - shop_postgres:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U shop_prod -d shop_prod"]
      interval: 10s
      timeout: 5s
      retries: 10
    restart: unless-stopped
    cpus: 1.0
    mem_limit: 1024m

volumes:
  shop_postgres:
  shop_uploads:
```

生产 env 同时包含 `POSTGRES_DB=shop_prod`、`POSTGRES_USER=shop_prod`、`POSTGRES_PASSWORD=<高强度密码>`；Compose 通过 `env_file` 将它们传给数据库容器。不要把密码硬编码进 Compose 文件。

## 5. Apache 接入方案

申请一个尚未被现有站点使用的域名，例如 `shop.example.com`，将 DNS A 记录指向该服务器公网 IP。为该域名新增独立 Apache 虚拟主机，不修改其他已有虚拟主机。

逻辑如下：

```apache
<VirtualHost *:443>
    ServerName shop.example.com
    DocumentRoot /srv/shop/frontend

    <Directory /srv/shop/frontend>
        Require all granted
        Options -Indexes
        AllowOverride None
    </Directory>

    ProxyPreserveHost On
    ProxyPass        /api/ http://127.0.0.1:5600/
    ProxyPassReverse /api/ http://127.0.0.1:5600/
</VirtualHost>
```

实施时还需：

- 按当前 Lighthouse/Apache 的证书管理方式为新域名申请和续期 TLS 证书；
- 确认 Apache 已启用 proxy/http 所需模块；
- 用 `apachectl configtest`（或该 Lighthouse Apache 对应的配置检测命令）验证后，再优雅重载；
- 在 DNS 和证书完成前，不进行公网切流。

## 6. 数据库迁移策略

### 6.1 基本原则

- Mac 开发库、测试库、生产库必须彼此独立，数据不需要一致；
- 所有环境应执行同一组 Alembic migration，保证**结构版本一致**；
- migration 与功能代码在同一个 Git 提交、同一个镜像版本中发布；
- 绝不把生产数据库内容、`.env.production` 或上传文件提交到 Git；
- 不让 API 容器在每次启动时自动执行 `alembic upgrade head`，避免扩容或重启时并发迁移。

### 6.2 新增一张表的开发到上线流程

```text
Mac：修改模型
  -> 生成 migrations/versions/<revision>_add_orders.py
  -> alembic upgrade head（本地库）
  -> 测试通过并提交代码 + migration
  -> PR / merge 到 main
  -> CI 构建镜像 shop-api:vX.Y.Z
  -> 服务器用 vX.Y.Z 的临时容器执行 migration
  -> migration 成功后切换正式 API 至 vX.Y.Z
```

服务器执行 migration 的方式：

```bash
IMAGE_TAG=v1.3.0 docker compose -f /srv/shop/compose.production.yaml \
  run --rm api alembic upgrade head
```

此命令创建一个短生命周期的**新版本** API 镜像容器。它连接同一个生产 PostgreSQL 数据卷，执行完自动删除；数据库中的 `alembic_version` 会记录已执行版本。它不是进入旧的运行中容器执行命令。

### 6.3 兼容性规则

新增表、新增可空列、添加索引通常可以先迁移再发布新代码。删除列、重命名列、把字段改为非空/改类型等破坏性变更采用“扩展—迁移—收缩”：

1. 先新增新字段或兼容逻辑，新旧代码都能运行；
2. 回填历史数据并验证；
3. 新版本稳定后，再以新的 migration 删除旧字段与兼容代码。

生产已有真实数据后，不应贸然用 `alembic downgrade -1` 删除表或字段。优先新增“前向修复 migration”，必要时从发布前备份恢复。

## 7. 发布、验证与回滚

### 7.1 发布前检查清单

- [ ] PR 已合并，CI 测试、镜像构建完成；
- [ ] 发布版本为不可变 tag，例如 `v1.3.0`，不用 `latest`；
- [ ] 迁移已在开发/预发布库验证；
- [ ] 已评估 migration 是否向后兼容；
- [ ] 生产数据库和上传目录已完成备份；
- [ ] `.env.production` 已补齐新变量，且不含在日志或命令历史中；
- [ ] 目标域名 DNS、证书、Apache 反代配置已验证。

### 7.2 推荐的发布脚本顺序

```bash
# 0. 指向唯一、已验证的版本
export IMAGE_TAG=v1.3.0

# 1. 拉取新镜像（不会立刻替换运行服务）
docker compose -f /srv/shop/compose.production.yaml pull

# 2. 备份数据库；备份文件写入 /srv/shop/backups 并设置保留策略
docker compose -f /srv/shop/compose.production.yaml exec -T db \
  pg_dump -U shop_prod shop_prod | gzip > /srv/shop/backups/shop-v1.3.0-pre.sql.gz

# 3. 使用新镜像执行一次性 migration；失败则停止发布
IMAGE_TAG="$IMAGE_TAG" docker compose -f /srv/shop/compose.production.yaml \
  run --rm api alembic upgrade head

# 4. 将 API 切至新镜像；不重建数据库
IMAGE_TAG="$IMAGE_TAG" docker compose -f /srv/shop/compose.production.yaml \
  up -d --no-deps api

# 5. 健康检查、关键接口与页面验收
curl -fsS http://127.0.0.1:5600/health
```

`/health` 需要由应用提供；若当前项目没有该接口，应先补充一个不泄露敏感信息的健康检查端点。

### 7.3 回滚

| 情况 | 处理方式 |
|---|---|
| 新代码故障，但 schema 对旧代码仍兼容 | 将 `IMAGE_TAG` 切回上一稳定版本，再 `up -d --no-deps api` |
| migration 未开始或迁移失败 | 不切换 API；根据错误修复后重新执行 |
| migration 已成功但新代码故障 | 优先回滚代码；仅当 migration 明确无数据风险且已演练，才考虑 `alembic downgrade` |
| 数据损坏/误操作 | 停止写入，使用发布前 `pg_dump` 备份按恢复预案处理 |

## 8. 日常开发与维护规范

### 开发者工作流

```text
feature 分支开发
  -> 本地 PostgreSQL 执行 migration 与测试
  -> 提交代码 + migration
  -> Pull Request
  -> 合并 main
  -> CI 构建带版本 tag 的镜像
  -> 服务器按发布脚本发布
```

- 不在生产服务器 `git pull` 后手改代码；
- 不在运行中的生产容器内编辑代码；
- 不使用 `latest` 作为发布依据；
- 不把生产密钥、数据库导出、上传文件纳入 Git；
- 发布记录应保留：时间、操作者、Git commit、镜像 tag、migration revision、备份文件名、验证结果。

### 监控与备份

- 每日 PostgreSQL 逻辑备份，至少保留 7～14 天；定期演练一次恢复；
- 上传文件采用每日增量/全量备份策略，并与数据库备份同周期保留；
- 监测磁盘利用率、容器重启次数、API 错误率、PostgreSQL 健康检查；
- 对 API 和数据库日志做轮转，避免 40 GiB 系统盘被日志占满；
- 每月安排一次系统与镜像安全更新评估，更新前先备份并在维护窗口执行。

## 9. 实施顺序与待确认事项

建议拆成四个可验证阶段：

1. **代码准备**：补 Dockerfile、Compose、Alembic、生产 CORS/环境变量、`/health`；在 Mac 上完成容器化开发验证。
2. **服务器基础**：确认域名与 DNS、安装 Docker、建立 `/srv/shop`、生产 env、备份目录和数据库容器；此阶段不接入公网流量。
3. **入口接入**：构建前端静态产物，新增 Apache 虚拟主机和 TLS，先以健康检查验证，再切 DNS/流量。
4. **运营固化**：GitHub Actions 构建镜像、发布脚本、备份定时任务、监控告警和回滚演练。

实施前需要业务方确认：

- 商城使用的正式域名/子域名；
- 镜像存储位置（推荐 GitHub Container Registry）；
- PostgreSQL 与上传文件的备份保留天数及异地备份位置；
- 可接受的发布维护窗口；
- 现有 MariaDB、SSH 安全策略和系统升级是否另开维护任务处理。
